# ADR 0008 — Inbound Mailbox Consumption and Signal Decryption

- Status: Accepted
- Date: 2026-10-02

## Context

Slice 7 established the Android outbound message boundary: a real libsignal ciphertext can be produced from an established, durable session and submitted through the existing server ciphertext-transport contract.

The server already exposes a device-scoped mailbox containing opaque ciphertext envelopes plus an idempotent per-device acknowledgment operation. Android therefore needs a receive-side cryptographic boundary that consumes those envelopes without prematurely treating them as processed.

The inbound path also mutates the same Signal `SessionRecord` used by outbound encryption. Correct persistence ordering and shared serialization are therefore required before mailbox consumption can safely be treated as delivered.

## Decision

### 1. Existing server mailbox is the input boundary

Android consumes the existing:

- `GET /api/e2ee/mailbox?limit=N`
- `POST /api/e2ee/mailbox/ack`

contracts without changing or extending the server API.

Mailbox entries are scoped by the server to the authenticated session's bound device. The Android processor handles a small batch sequentially and acknowledges individual message IDs.

### 2. Existing session metadata is the inbound routing key

Each mailbox entry supplies `senderDeviceId`. Android resolves it against the existing `SignalSessionEntry` created by outbound session establishment.

If the sender device is not already known locally:

- do not discover it;
- do not claim an OTPK;
- do not create a new Signal session;
- do not acknowledge the entry;
- continue processing other entries.

Android does not invent a reverse mapping from `senderUserId` to the username/signal-device address.

### 3. Envelope type is authoritative

The server-provided `envelopeType` is the sole parser discriminant:

- `PREKEY_INIT` → `PreKeySignalMessage` → libsignal PREKEY decrypt;
- `RATCHET` → `SignalMessage` → libsignal RATCHET decrypt.

Unknown envelope types, malformed Base64/ciphertext, and invalid crypto/session state fail closed.

No parser fallback or type inference is performed.

### 4. Durable SessionRecord is the receive-side commit boundary

Successful inbound decrypt mutates the Signal session state. Android therefore uses this invariant:

`FETCH → DECRYPT → EXPORT → SEAL → ACK`

The mutated `SessionRecord.serialize()` bytes are sealed before the mailbox entry is acknowledged.

A decrypt or seal failure never acknowledges the entry.

The same durable session handle/namespace established by Slice 6 is reused; no second session store or persistence framework is introduced.

### 5. Duplicate delivery semantics

The actual libsignal 0.86.5 behavior was experimentally verified before implementation:

- replaying a successfully processed PREKEY ciphertext throws `DuplicateMessageException` and does not mutate the persisted session state;
- replaying a successfully processed RATCHET ciphertext throws `DuplicateMessageException` and does not mutate the persisted session state;
- PREKEY duplicate detection remains effective even when the consumed OTPK record is absent;
- after a successful PREKEY decrypt, the receiver has a sender chain and the next outbound encryption is WHISPER/RATCHET.

Therefore `DuplicateMessageException` is the only crypto outcome treated as proof that the mailbox entry was already processed. The entry may be acknowledged without delivering plaintext again.

All other decrypt failures remain unacknowledged and therefore eligible for later redelivery.

### 6. Shared outbound/inbound session serialization

Outbound and inbound operations mutate the same `SessionRecord`.

Android therefore uses the per-remote-device `SessionDeviceLocks` holder from both `MessageSender` and `InboxProcessor`.

The lock covers the complete session mutation window through successful SessionRecord sealing. ACK is outside the lock because the server operation is idempotent and does not mutate the local Signal session.

### 7. Identity and private-material handling

Remote identity remains pinned to the existing session metadata and is checked before/after inbound decryption.

Local identity, signed-prekey, Kyber, and OTPK private records are restored from the existing Keystore-backed vault. Missing/corrupt material fails closed; no replacement identity or prekey material is generated by the inbound path.

Plaintext is returned only in memory. Android does not persist inbound ciphertext or plaintext as part of this slice.

### 8. OTPK and Kyber lifecycle boundary

Successful PREKEY processing consumes the OTPK within the live libsignal store, but the historical private OTPK record remains in the vault. Durable cleanup/reconciliation belongs to the future OTPK replenishment/inventory lifecycle; the server's atomic claim state is authoritative.

Kyber last-resort material remains durable. Process-scoped `markKyberPreKeyUsed` tracking matches libsignal's in-memory reference semantics and preserves crash-before-session-seal recovery. This slice does not persist a separate Kyber-used set.

## Consequences

- Android can now consume existing server mailbox envelopes and establish the inbound Signal decryption boundary without introducing new server APIs.
- A mailbox entry is not acknowledged until its corresponding mutated Signal SessionRecord is durably sealed.
- Ambiguous ACK outcomes converge through mailbox redelivery; a later duplicate decrypt can prove prior processing and permit acknowledgment without duplicate plaintext delivery.
- Unknown senders remain unprocessable in this slice rather than silently inventing a new address/discovery protocol.
- Android still lacks a local message/history store, so decrypted plaintext is currently returned to the headless caller rather than displayed or persisted.
- OTPK replenishment, Kyber rotation, history/cursor reconciliation, realtime delivery, Companion flows, identity verification UX, and backup remain outside this decision.
- The libsignal AGPL-3.0-only distribution decision remains outstanding.

## Scope

This ADR covers inbound mailbox consumption, Signal PREKEY/RATCHET decryption, receive-side SessionRecord persistence, per-entry acknowledgment, duplicate-delivery handling, and shared outbound/inbound session serialization.

It does not define local message persistence, history synchronization, realtime/push delivery, OTPK replenishment, Kyber rotation, Companion approval/recovery, identity verification UI, or backup/restore.
